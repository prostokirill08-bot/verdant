# Архитектура

```
 Клиент ──► Сайт (FastAPI) ─┐                         ┌─► Yandex Cloud (YandexGPT, YandexART) / GigaChat
 Клиент ──► Telegram Bot API ┤                         │
                             ▼                         │
                     PostgreSQL / SQLite ◄──── Воркер (python -m app.worker)
                     (CRM, заказы, платежи,     ├─ очередь задач (повторы, идемпотентность)
                      очередь, журнал агентов,  ├─ планировщик (МСК)
                      события, финансы)         ├─ Telegram long polling
                             ▲                  ├─ агенты: CEO, Research, Sales, Marketing,
 ЮKassa ── вебхук ───────────┘                  │          Production, QC, Support, Finance
                                                └─ Chromium (Playwright) — рендер слайдов
 Владелец ◄── отчёты/эскалации (Telegram, e-mail) · админка /admin
```

## Стек и причины выбора
| Часть | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12+ | одна экосистема для веба, ML (ONNX) и автоматизации |
| Веб | FastAPI + Jinja2 | сайт, кабинет, вебхуки и админка в одном процессе без сборки фронтенда |
| БД | PostgreSQL (прод), SQLite (разработка) | SQLAlchemy 2.0; очередь работает на обеих |
| Очередь | таблица `tasks` в БД | без Redis/брокеров — меньше инфраструктуры; атомарный захват `UPDATE … WHERE status IN (…)` |
| LLM | YandexGPT / GigaChat | доступны резиденту РФ, оплата в рублях |
| Рендер | HTML-шаблон → Chromium → JPG | кириллица всегда без ошибок, точная вёрстка, авто-подгонка текста |
| Вырезка | U²-Net ONNX (Apache-2.0) + заливка белого фона | бесплатно, локально, без передачи фото третьим лицам |
| Платежи | ЮKassa (самозанятый) / ручной СБП | доступно самозанятому |

## Модули (`app/`)
- `config.py` — все настройки из переменных окружения.
- `models.py` — Client, Lead, Message, Order, OrderItem, Payment, Expense, Task, AgentRun, Event, ContentPost, Escalation, Setting.
- `queue.py` — `enqueue` (уникальный `idempotency_key`), `claim_next`, `run_task`: повтор через 30с·2ⁿ (≤1 ч), после `max_attempts` → `dead` + эскалация. Зависшие `running` > 20 мин освобождаются.
- `events.py` — журнал событий (из него считаются отчёты), эскалации, настройки времени выполнения.
- `agents/` — агенты (см. AI_AGENTS.md). `base.py`: учёт запусков, стоимости, дневной бюджет AI, `ask_llm` с обязательным запасным алгоритмом и валидацией ответа.
- `imaging/` — вырезка, палитры, иконки, рендер.
- `payments/service.py` — создание платежей, вебхук, `mark_paid` (идемпотентно).
- `integrations/` — Telegram Bot API, SMTP.
- `web/` — сайт, кабинет, вебхуки, админка.
- `reports.py` — ежедневный отчёт.
- `worker.py` — цикл воркера, расписание, Telegram-опрос, бэкап.

## Жизненный цикл заказа
`preview_queued → preview_ready → awaiting_payment → paid → in_production → ready → delivered`
ответвления: `revision` (правки) · `needs_human` (QC не пройден) · `cancelled`.

Задачи: `make_preview` → (оплата) `produce_order` → `produce_item` (на каждый товар) → `finalize_order` → `deliver_order` → `notify_owner`.

## Защита от двойной обработки
- Платёж: уникальная пара (provider, provider_payment_id); статус ЮKassa перепроверяется GET-запросом; сумма сверяется с тарифом; `mark_paid` не срабатывает повторно.
- Производство/доставка: ключи `produce_order:{id}`, `produce:{item}:r{revision}`, `deliver:{order}:{версия}`.
- Планировщик: ключ `sched:{задача}:{минута}` — безопасно при нескольких воркерах.

## Безопасность
- Секреты только в `.env` на сервере (в git — `.env.example`).
- Админка: HTTP Basic + CSRF-токен (HMAC, сутки) на все POST.
- Файлы заказа доступны только по секретному токену заказа; результат — только после оплаты.
- Загрузки: ≤15 МБ, проверка что это изображение, перекодирование.
- Ограничение частоты заявок с IP, ловушка для ботов.
- Персональные данные в LLM не передаются (только название и факты о товаре).

## Мониторинг, логи, бэкапы
- `/healthz` — 503, если воркер не подавал сигнал > 3 мин (подключить внешний мониторинг).
- Логи процессов — stdout (docker logs); журнал агентов и задач — в админке.
- SQLite: онлайн-бэкап ежедневно, 14 копий. Postgres: `scripts/backup_pg.sh` по cron хоста.

## Масштабирование
Несколько воркеров на одной БД работают корректно (атомарный захват задач). Узкое место — рендер (~0,5 с/слайд на 1 vCPU): 1 воркер ≈ 300+ товаров в час.
